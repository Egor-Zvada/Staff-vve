# Staff V2

Внутренний веб-сервис учёта прихода и ухода сотрудников. Терминал работает с QR-сканером, который передаёт код как клавиатура; сотруднику достаточно поднести карточку. Обычный браузер также поддерживается.

## Возможности

- Автоприём скана без Enter, обработка Enter и отдельный режим медленного ручного набора. Начальный интервал тишины — 100 мс; значение настраивается под оборудование.
- Серверное время `Asia/Sakhalin`. По умолчанию AUTO выбирает приход с 05:00 до 12:00, уход после 12:00; необычное событие можно выбрать явно.
- Отдельные исходные события и официальные значения дня. Ручная запись «сейчас» не считается поздней правкой; внесение прошлых дат, более раннего времени и замена отметок фиксируются с временем получения сервером.
- Группы расписаний, версии назначений, календарные исключения и допуски. Отметки в обычный выходной сохраняются без влияния на статистику пунктуальности.
- Сотрудники, увольнение и восстановление с сохранением истории. ADMIN и MODERATOR назначаются существующим сотрудникам; административный вход использует код пропуска и пароль.
- Табель, показатели, фильтры, импорт CSV/XLSX/XLS с предпросмотром и атомарным применением; экспорт CSV/XLSX/PDF.
- Печать одиночных и массовых пропусков: локальные QR и шрифты, карточка ID-1, произвольные листы и этикетки, координаты в миллиметрах, PNG/ZIP/PDF, калибровка и двусторонняя раскладка.
- Привязка и отзыв NFC UID. Реальный считыватель должен отдавать стабильный UID в поддерживаемом формате; режим выдачи не создаёт отметку посещаемости.
- Светлая и тёмная темы, встроенная справка, состояние сервиса и резервное копирование.

## Коды сотрудников

Внутренний `employees.id` остаётся постоянным ключом для истории. Человек пользуется публичным `pass_code`:

- существующие числовые карточки сохраняют код, например `007`;
- новый сотрудник получает случайный `VVE-XXXX-XXXX-XXXX` из 60 бит криптографической случайности;
- перевыпуск меняет код у того же сотрудника и отключает прежние QR; посещаемость и независимые NFC-карты сохраняются;
- при действующем или неподтверждённом Wallet сначала требуется подтверждённый отзыв старого пропуска.

Для новых строк импорта оставьте ID пустым: сервис создаст случайный код и назначит действующую группу по умолчанию. Явный старый числовой ID используется для переноса уже выпущенных карточек. Существующего сотрудника с кодом VVE можно обновлять по этому коду. Старый код после перевыпуска не принимается как запасной способ входа.

## Wallet

Необязательный модуль использует WalletWallet. Выдача выполняется только явным действием администратора или в режиме выдачи терминала. Просмотр, обновление статуса и печать берут сохранённый пакет и не создают новый пропуск.

Оформление пакета: верхний заголовок **«ПРОПУСК»**, поле **«ФИО»** с фамилией, именем и отчеством, отдельный код ID и QR действующего кода. Отчество пропускается, если его нет в карточке сотрудника.

Используются platform credentials. Для Free platform готовые пакеты не редактируются через PUT: смена содержимого требует отзыва и явного нового выпуска с учётом квоты. Неоднозначный результат внешнего запроса блокирует повторную выдачу до проверки. API-ключ хранится только на сервере. Во внешний сервис передаются разрешённые поля пропуска — ФИО и код; сведения о посещаемости туда не отправляются.

Обратная сторона печатной карточки может содержать локально сформированный QR сохранённой ссылки добавления в Wallet. Двусторонний PDF чередует лицо и оборот; зеркалирование учитывает ориентацию бумаги, сторону переворота и смещение принтера. Добавление Wallet на телефоне требует доступа к внешней платформе; основной учёт посещаемости работает в локальной сети.

## Стек и структура

PHP 8.4+, Symfony 7.4, Twig, Doctrine DBAL, MariaDB, Nginx и PHP-FPM. QR — Endroid, таблицы — PhpSpreadsheet, PDF — Dompdf. Все ресурсы основного интерфейса локальные. Постоянные процессы Node.js, Redis и Docker приложению не нужны.

```text
app/src/           Контроллеры, доменная логика и доступ к БД
app/templates/     Интерфейс Twig
app/public/        Единственный веб-корень, локальные ресурсы
app/migrations/    Основная схема и добавочные SQL-миграции
app/tests/         Изолированные SQL, браузерные и интеграционные проверки
deploy/            Подготовка Debian, обновление, перенос и резервное копирование
```

`vendor` воспроизводится по `app/composer.lock`. Рабочие БД, сертификаты, ключи, `.env.local`, сессии, резервные копии и выгрузки людей не входят в репозиторий.

## Развёртывание

Сценарии `deploy/` рассчитаны на Debian 13 с systemd и установкой приложения в `/opt/staff-v2/app`. Подготовка окружения требует root; приложение работает от `www-data`. В сценариях владения исходниками используется учётная запись сопровождения `codex-maint` — создайте её или адаптируйте владельца перед запуском.

1. Подготовьте PHP 8.4 CLI/FPM с `pdo_mysql`, `gd`, `mbstring`, `xml`, `zip`, `curl`, `intl` и `pdo_sqlite` для проверок; Nginx, MariaDB, Composer и `fonts-dejavu-core`. `deploy/bootstrap.sh` содержит профиль окружения для небольшого LXC, включая сахалинское время.
2. Поместите приложение в `/opt/staff-v2/app` и установите зависимости:

   ```bash
   cd /opt/staff-v2/app
   composer install --no-dev --prefer-dist --optimize-autoloader --no-interaction
   ```

3. Используйте `app/.env.example` как перечень конфигурации. Секреты задайте в серверном `.env.local`. `deploy/generate-secrets.py` создаёт отдельный локальный файл начальных реквизитов; `deploy/setup.php` ожидает его на сервере в `/tmp/staff-v2-secrets.json`, создаёт БД и служебный начальный доступ, затем удаляет входной файл. Генератор не перезаписывает существующие реквизиты.
4. Укажите собственное имя сайта в Nginx и разрешённых хостах Symfony. Веб-корень — только `app/public`; PHP исполняется через `public/index.php`. Установите доверенный сертификат и ключ в `/etc/staff-v2/server.crt` и `/etc/staff-v2/server.key`. Временный самоподписанный сертификат предназначен для первоначальной проверки.
5. Скопируйте DejaVu Sans Regular/Bold в `app/public/assets/DejaVuSans.ttf` и `DejaVuSans-Bold.ttf`; эту операцию выполняет `deploy/activate.sh`. Каталог `app/var` должен быть доступен на запись `www-data`.
6. Заполните начальные группы через админку либо `deploy/seed-defaults.php`, затем назначьте персональных администраторов. Перед переключением терминалов задайте начало учёта первым рабочим днём нового сервиса: подготовка и перенос людей не означают, что они уже должны были отмечаться в Staff V2. `deploy/configure-administrators.php` получает входные реквизиты из отдельного временного JSON и удаляет его после применения.
7. Перед обновлением сделайте резервную копию. `deploy/update.sh` обновляет код и очищает кэш, сохраняя настройки и реквизиты. Добавочные миграции, включая `wallet.sql` и `pass-codes.sql`, применяются отдельно **до** запуска кода, который использует новые поля. Изменение схемы не переносит старые отметки автоматически.

Параметры PHP-FPM и MariaDB в сценариях — начальные значения для LXC с 2 ГБ RAM и двумя CPU. Настройте их под фактическую нагрузку. Диагностические сценарии Wallet запускайте отдельно: сценарий, который явно выпускает тестовый пропуск, расходует квоту платформы.

## Перенос сотрудников

`deploy/migrate-people.php` принимает проверенный JSON справочника. По умолчанию выполняется только чтение и показ счётчиков. Для применения нужны `--commit` и `--sha256` утверждённого файла; для индивидуальной карты расписаний дополнительно нужны `--schedule-map` и `--schedule-map-sha256`.

Перенос сохраняет числовые ID, исходное написание ФИО и статус увольнения, резервирует следующий номер и проверяет неизменность количества записей посещаемости. Повтор того же переноса обрабатывается идемпотентно. Пароли и роли из старого сервиса не копируются. Реальные выгрузки людей храните отдельно от исходников.

## Проверки

Из корня репозитория, с включёнными `pdo_sqlite` и `mbstring`:

```bash
php app/tests/domain.php
php app/tests/employee-service.php
php app/tests/wallet.php
php app/tests/exports.php
```

Эти проверки используют изолированную SQLite и подставной HTTP-транспорт. Они проверяют время и календарь, поздние изменения, сохранность истории, коды и перевыпуск, импорт, состояния и квоту Wallet. Настоящий API-ключ и production DB для них не нужны. Дополнительные режимы тестов MariaDB допускают только специально подготовленную пустую тестовую БД.

Для браузерных проверок нужен Node.js и Playwright с установленным Chromium или поддерживаемым браузерным каналом:

```bash
cd app
npm install
npx playwright install chromium
npm test
```

Изолированные UI-проверки используют вымышленные данные и подставные ответы. `npm run test:browser`, `test:acceptance`, `test:wallet` и `test:reports` требуют отдельного QA-сайта, тестовых реквизитов и подготовленных записей. `npm run test:production` предназначен для чтения опубликованного сервиса. QA-проверки не должны запускаться против рабочей БД.

Параметры интеграционных браузерных проверок:

| Переменная | Назначение |
|---|---|
| `STAFF_TEST_ORIGIN` | Полный HTTPS-адрес отдельного QA-сайта, например `https://staff.example.internal:8443` |
| `STAFF_TEST_IP` | Адрес, на который браузер направляет тестовое имя; по умолчанию `127.0.0.1` |
| `STAFF_TEST_ACCESS_FILE` | Приватный JSON тестовых реквизитов; содержимое не входит в репозиторий |
| `STAFF_PRODUCTION_ORIGIN` | Адрес сайта для проверки чтения опубликованного сервиса |
| `STAFF_PRODUCTION_ACCESS_FILE` | Отдельные реквизиты для проверки опубликованного сервиса |
| `STAFF_TEST_OUTPUT_DIR` | Каталог отчётов, изображений и скачанных тестовых файлов вне Git |
| `STAFF_PLAYWRIGHT_MODULE` | Необязательный путь к готовому модулю Playwright вместо локального `node_modules` |
| `STAFF_BROWSER_CHANNEL` | Необязательный канал браузера; Windows использует Edge по умолчанию, Linux — Chromium Playwright |

Для печати дополнительно проверьте PNG/PDF и физический контрольный лист на вашем принтере в масштабе 100%. Тайминг HID-сканера, UID NFC и добавление Wallet на реальные телефоны проверяются на соответствующем оборудовании.

## Эксплуатация

Настройки групп, календаря, интервалов сканирования, допусков и оформления доступны в админке. Резервное копирование выполняется таймером systemd; независимая внешняя копия требует отдельного подключённого хранилища. Вместе с БД сохраняется защищённый архив серверных реквизитов и HTTPS-сертификата; доступ к нему должен быть только у владельца сервиса. `deploy/verify-restore.php` проверяет восстановление отдельно от рабочей БД.

QR подтверждает предъявленный код карточки. Физическую личность владельца и местонахождение человека этот механизм сам по себе не определяет. При анонимной ручной отметке сохраняются заявленный сотрудник, источник и серверное время; автор не становится достоверно установленным пользователем без административного входа.
